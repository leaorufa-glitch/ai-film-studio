## 2. 问题 A：原 Provider 恢复与一致性

`apps/api/main.py` 增加统一的 `generation_provider`，从失败 Job 的事件 metadata、不可变执行快照的 Provider 记录以及已知原 Model Profile ID 恢复 Provider。

- Admin 显式把恢复出的原 Provider 传给同一个 Creator `generate` 路径。
- Creator 技术重试未传 Provider 时，由后端恢复原 Provider；显式传入不同 Provider 则拒绝，不允许技术重试切换通道。
- Provider 来源互相冲突、未知或无法恢复时明确拒绝，不猜测为 Darl。
- 历史 Darl Job 没有 Provider 字段时，仍可由原 `h3-darl` Profile 确定 Darl；当时的旧备用直连 Profile 不会被错误回落到 Darl。现行系统拒绝执行旧非 Darl Provider Job。
- 可用性检查针对原 Provider，不针对默认 Darl。原 Provider 未配置、停用或离线时返回 `503 / PROVIDER_UNAVAILABLE`，不提交到其他 Provider。
- 新 Job、Runtime、事件与成本快照仍记录实际 Provider，保留 `retry_of` 和原任务关系。

Creator 的 `Workspace.tsx` 只调整技术重试按钮：使用原 Job 的 Provider 可用性，不再用最新 Brief 的 readiness 或“本次视频服务”选择阻挡原任务重试；请求不传新的 Provider，服务端仍进行完整安全检查。普通生成与 Creative Regenerate 继续使用用户选择的 Provider 和当前制作方案。

## 3. 问题 B：原 Brief 与执行输入锁定

网站 Technical Retry 复用失败 Job 的原 Compiled Task，不重新编译最新 Brief。原 Prompt、Brief ID/version、Model Profile ID/version/snapshot、参数、画幅、时长、Reference Bindings、continuation 与 control media snapshot 保持原执行快照。

Production Core 仅对既有 `preflight` 增加可选 `retry_of` 参数，并由 `create_job` 传入；默认预检和领域对象结构保持不变。

- 只有原失败 Job 的输入与原持久化任务一致，且重试任务执行载荷完全相同时，才允许历史输入预检。兼容已有调用方为等价载荷分配新 Task ID；网站直接复用原 Task ID。
- 原 Brief、Profile、Reference Binding 的明确版本必须存在；Reference Binding 和 Profile 与原快照必须一致。缺失版本、缺失输入或快照不一致会拒绝，不静默读取最新版。
- 技术重试允许已归档且可恢复的 Brief / Profile / Reference 版本，普通新生成仍拒绝过期输入。
- 模型能力、参数、引用来源存在性、语义哈希、当前上游 Canonical / Selection 和 Stable Tail 等安全检查继续执行。历史输入模式不是跳过所有预检。
- Brief 更新不修改旧 Job / Task / Take；使用新 Brief 必须明确进入 Creative Regenerate，产生独立任务和创作尝试，而不是技术重试。
- 保留最新失败 Job 限制、可重试错误类别、最多两次技术重试、请求去重和提交互斥。
- 本轮没有回写或迁移已有项目数据。缺失必要来源信息的旧记录被安全拒绝，而不是补造来源。
